================================================================================
0. PURPOSE OF THIS FILE
================================================================================

This file gives Codex and local AI workers the full project context needed to plan,
architect and progressively build the Drinklivery MVP.

Drinklivery is a premium cocktail delivery platform. The initial pilot market is
Panama. The project must be built as a clean, modular, testable web application
that can begin as a simple single-market MVP but later evolve into a reusable
multi-market platform owned by Lazy Software Inc.

This file is intentionally detailed. Local AI workers must read this before
implementing backend or frontend tasks.

IMPORTANT:
- Do not build the whole app in one task.
- Use microtasks.
- One task = one intention.
- Always preserve the business model and ownership separation.
- Always preserve compliance-sensitive behavior around alcohol orders.
- Backend first. Frontend later.
- Tests are mandatory for backend behavior.

1. BUSINESS CONTEXT
================================================================================

Project name:
Drinklivery

Initial market:
Panama

Initial operating model:
A local operating partner in Panama is a bartender and can handle local permits,
cocktail preparation, sourcing, operations and compliance. Adrian / Lazy Software
owns the software.

Core business idea:
Drinklivery is not a liquor bottle delivery app. It is a premium cocktail delivery
experience focused on:
- ready-to-serve cocktail packs
- cocktail kits
- mocktail packs
- event-oriented bundles
- premium packs for meetings, birthdays, Airbnbs, after-office events and home plans

The product is not "alcohol delivery".
The product is "premium cocktail experiences delivered".

Positioning:
A digital-first premium cocktail brand powered by its own app, lightweight
operations and controlled delivery.

Strategic phrase:
"The bar arrives at your home."

Alternative positioning:
"Premium cocktails for your gatherings, prepared by a bartender and delivered
ready to serve."

Business thesis:
Instead of spending heavily on a physical bar, rent, staff and front-of-house
infrastructure, Drinklivery uses:
- a premium mobile-first storefront
- scheduled ordering
- controlled production
- small catalog
- operating limits
- compliance-aware delivery
- software-driven operations
- strong brand experience through the app

This is meant to reduce infrastructure costs while keeping the business legal,
premium and scalable.

3. LEGAL / COMPLIANCE STRATEGY
================================================================================

Important:
This project involves alcohol. Compliance must be treated as a first-class
business requirement. The app must support responsible delivery workflows.

The local partner is responsible for confirming all required permits in Panama.

Do not present the business as:
"selling cocktails from home"

Use this language instead:
"authorized micro-lab for premium cocktail preparation, digital scheduled orders
and controlled delivery"

The software must support:
- legal drinking age confirmation before checkout
- responsible drinking messaging
- in-person handoff for alcoholic orders
- ID/document check at delivery
- ability to reject delivery if receiver is underage, absent or visibly intoxicated
- configurable operating hours
- configurable delivery zones
- ability to disable orders on restricted dates
- order status for failed age verification
- internal traceability of delivery verification

MVP must avoid storing sensitive document images unless explicitly approved later.
For MVP, store:
- receiver name
- whether document was checked
- whether receiver is an adult
- who verified
- timestamp
- notes if delivery failed

4. BUSINESS RULES
================================================================================

Core rules:

1. Drinklivery does not sell standalone liquor bottles in the MVP.
2. Drinklivery sells cocktail packs, cocktail kits, mocktail packs and event-oriented bundles.
3. Orders are scheduled by default, not instant delivery.
4. Customer must confirm legal drinking age before checkout for alcoholic products.
5. Alcoholic products require in-person delivery.
6. Alcoholic orders cannot be left at reception, lobby, door, building entrance or with minors.
7. Admin/operator can reject orders based on delivery area, schedule, availability or compliance rules.
8. MVP starts with one tenant/operation: Drinklivery Panama.
9. The software is owned by Lazy Software / Adrian.
10. The local operator is responsible for permits, preparation and compliance in Panama.
11. The app must be mobile-first.
12. The app must feel premium, controlled and trustworthy.
13. Production capacity must be limited at the system level.
14. The system must support order rejection/cancellation.
15. The system must support delivery verification before marking alcoholic orders as delivered.
16. The system should support non-alcoholic mocktail products.
17. Payment can be manual at the beginning.
18. WhatsApp can be manual/link-based at the beginning.
19. No marketplace model in the MVP.
20. No native app in the MVP.

6. TECHNICAL STACK DECISION
================================================================================

Recommended backend stack:
- Python
- Django
- Django REST Framework
- pytest
- pytest-django
- SQLite for initial local development
- PostgreSQL later for staging/production
- django-cors-headers
- python-dotenv or django-environ

Recommended frontend stack later:
- React
- Vite
- Tailwind CSS or clean CSS modules
- Mobile-first layout
- Netlify or Vercel for deployment

Backend choice:
Use Django + Django REST Framework, not FastAPI, for this MVP.

Reason:
This project needs models, admin, users, orders, status, products, compliance logs,
delivery zones and operational dashboards. Django provides structure and speed
for business apps.

Architecture:
- Monolithic modular backend
- Separate Django apps by domain
- API-first for frontend
- Backend-first development
- Tests required for every business rule

Do not use:
- microservices
- Kubernetes
- Celery
- Docker as mandatory initial dependency
- complex settings split before needed
- premature payment integrations

================================================================================
10. ORDER STATUSES
================================================================================

Initial statuses:

PENDING
ACCEPTED
IN_PREPARATION
READY_FOR_DELIVERY
OUT_FOR_DELIVERY
DELIVERED
CANCELLED
REJECTED
FAILED_AGE_VERIFICATION

Rules:
- New public checkout orders start as PENDING.
- Admin can ACCEPT or REJECT.
- Admin can move ACCEPTED to IN_PREPARATION.
- Admin can move IN_PREPARATION to READY_FOR_DELIVERY.
- Admin can move READY_FOR_DELIVERY to OUT_FOR_DELIVERY.
- Alcoholic orders should not be marked DELIVERED without delivery verification.
- If age verification fails, status must become FAILED_AGE_VERIFICATION.
- CANCELLED must be available for operational cancellations.
- Status changes must create OrderStatusHistory records.

11. API ENDPOINT PLAN
================================================================================

Public storefront endpoints:

GET /api/health/

GET /api/public/{tenant_slug}/catalog/
Purpose:
- Return active categories, active products and active variants for tenant.

GET /api/public/{tenant_slug}/products/{product_slug}/
Purpose:
- Return public product detail.

GET /api/public/{tenant_slug}/delivery-zones/
Purpose:
- Return active delivery zones.

POST /api/public/{tenant_slug}/orders/
Purpose:
- Create customer, address, order and order items.
- Validate age confirmation for alcoholic orders.
- Validate product availability.
- Validate zone if delivery zone is included.
- Calculate subtotal, delivery fee and total.

GET /api/public/{tenant_slug}/orders/{order_code}/status/
Purpose:
- Return public status of a specific order.

Admin/internal endpoints:

GET /api/admin/orders/
GET /api/admin/orders/{id}/
PATCH /api/admin/orders/{id}/status/
PATCH /api/admin/orders/{id}/payment/
POST /api/admin/orders/{id}/delivery-verification/
GET /api/admin/products/
POST /api/admin/products/
PATCH /api/admin/products/{id}/
GET /api/admin/dashboard/summary/

Authentication:
- Do not implement authentication in BE-001.
- Later use Django auth/session or token auth for internal admin endpoints.
- Public endpoints must not require customer login in MVP.
